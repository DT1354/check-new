# 新生打卡控制台设计

## 目标

在现有打卡核心之上提供一个多账号控制台。管理员可管理账号、生成一次性邀请链接、手动执行单人或全部打卡、查看最终结果并配置飞书通知。每天 21:05 自动运行；失败账号关闭旧浏览器会话后等待 10 秒，只自动重试一次。

## 架构

前端是部署在 Cloudflare Pages 的 React 单页应用。服务器运行 FastAPI API、SQLite 数据库和单进程任务 Worker；Cloudflare Tunnel 把独立 API 子域名转发到服务器本地端口。前端与 API 使用精确 CORS 白名单、Secure HttpOnly 会话 Cookie 和 CSRF Token。

学校账号、密码、飞书 Webhook 与签名密钥使用 AES-256-GCM 加密；主密钥只从服务器 Credential 文件读取。管理员密码使用 Argon2id 哈希。邀请链接使用高熵随机 Token，数据库仅保存 Token 的 SHA-256 哈希，默认 24 小时过期且只能使用一次。

任务写入 SQLite 队列表，由单个 Worker 串行执行，避免多个 Chrome 同时抢占服务器资源。前端不展示浏览器内部步骤，也不持续轮询；只显示执行中、成功、失败，并在提交任务约 60 秒后、页面重新获得焦点或用户点击刷新时更新。

## 界面方向

界面采用克制的桌面原生风格：冷灰背景、连续白色面板、细边框、低阴影、清晰状态点和少量绿色/橙色/红色。顶部导航包含“今晚、账号、记录、设置”，账号列表右侧提供单人执行按钮，页面顶部提供全部检查并打卡和重试失败账号。邀请页面只有昵称、办事大厅账号、密码三项，不要求被邀请人注册。

## 失败与恢复

- 自动任务失败：新建浏览器会话并自动重试一次。
- 手动任务失败：保留结果，管理员可再次点击。
- 已经打卡：查询后直接标记成功，不重复提交。
- API 或 Worker 重启：排队任务仍保存在 SQLite；启动时回收超时的运行中任务。
- 飞书失败：不影响打卡结果，记录通知错误供管理员查看。
- Tunnel 配置：优先复用现有 Tunnel，新增独立 hostname 到本地 API 端口；上线前备份并验证原规则。
